# M0 — 트레이스 복원 검증 (스파이크) 결과

검증일: 2026-08-20 / 대상: 기획서 v2 §5.2 "최우선 검증 항목"

## 결론: 통과. M1 진행 가능.

> "실제 훅 트랜잭션 하나를 잡아서 callTracer 출력만으로 각 단계 금액이 복원되는지 확인할 것."

하나가 아니라 **187건**으로 확인했고, **187건 전부 복원됐다.** 커스텀 트레이서는 필요 없다.

| 코퍼스 | 고유 tx | 복원 성공 |
|---|---|---|
| Unichain 스왑 (최근 3,600블록) | 52 | 52 (100%) |
| Unichain 스왑 (20만 블록 이전, 독립 표본) | 33 | 33 (100%) |
| Unichain 유동성 변경 | 4 | 4 (100%) |
| Base 스왑 | 98 | 98 (100%) |
| **합계** | **187** | **187 (100%)** |

체인별로 보면 Unichain 89건 중 23건(25.8%), Base 98건 중 65건(66.3%)이 훅이 붙은 풀을 거쳤다.
관측된 서로 다른 훅은 Unichain 12종, Base 24종.

(표본은 "풀당 1건"으로 뽑았다. 훅 풀은 종류는 많지만 거래량이 적어서, 트랜잭션 단위로 무작위 표집하면
거래량 큰 무훅 풀 몇 개에 표본이 쏠린다. 같은 트랜잭션이 여러 풀을 거치는 경우가 있어
풀 표본 231개가 고유 트랜잭션 187건에 대응한다.)

## 1. 어떻게 검증했나 — "그럴듯해 보인다"가 아니라 기계적 증명

복원 결과가 맞는지를 두 개의 독립된 기준으로 확인했다.

**(1) 델타 제로 불변식.** v4는 `unlock()`이 끝나는 시점에 모든 (주소, 통화) 델타가 정확히 0이 아니면
트랜잭션을 되돌린다. 이미 체인에 올라간 트랜잭션이라면 실제로 0이었다는 뜻이다.
따라서 우리 복원 장부가 0으로 떨어지면 — 187건 전부 떨어졌다 — 모든 금액을 빠짐없이,
부호까지 정확히 집계했다는 게 증명된다. 한 건이라도 놓치면 잔차가 남는다.

**(2) 실제 토큰 이동과 대조.** `settle` 합계에서 `take` 합계를 뺀 값이 PoolManager로 실제 들어간
ERC20 Transfer / 네이티브 순증감과 통화별로 일치하는지 확인했다. 187건 전부 일치.

(1)은 내부 정합성, (2)는 외부 사실과의 일치. 둘 다 통과해야 PASS로 셌다.

## 2. 기획서의 핵심 전제(§5.1)가 수치로 확인됐다

훅이 값을 가져간 트랜잭션 중, **Transfer 이벤트에 훅 주소가 단 한 번도 등장하지 않는 비율**:

| 체인 | 훅이 값을 움직인 tx | Transfer 기반 도구에 안 보임 |
|---|---|---|
| Unichain | 12 | **9 (75.0%)** |
| Base | 48 | **32 (66.7%)** |

즉 기존 익스플로러로 보면 훅이 수수료를 가져간 사실 자체가 화면에 없다. 이게 해자다.

훅이 값을 가져가는 방식 (UI 엣지 타입 설계의 근거):

| 방식 | Unichain | Base |
|---|---|---|
| `swap` 리턴 델타 (beforeSwap/afterSwap) | 20 | 51 |
| ERC-6909 `mint` (PoolManager 내부 청구권) | 13 | 38 |
| `take` | 7 | 29 |
| `settle` / `settleFor` | 7 | 7 |
| `burn` | 0 | 6 |

`mint6909`가 두 번째로 흔하다는 게 중요하다. **ERC-6909 청구권은 PoolManager 밖으로 나가지 않으므로
ERC20 Transfer가 아예 발생하지 않는다.** Transfer 기반 도구가 구조적으로 못 보는 영역이다.

### 대표 사례

`0xe0a7208c…` (Unichain) — 실제 ERC20 Transfer는 **단 2건**. 그런데 복원하면:

```
swap    라우터 → PM      2,241,466 (token A)
swap    PM → 라우터      31,316,167,330,635,321,344 (token B)
hookFee PM → 훅          499        ← Transfer 이벤트 없음
mint    PM → 0xa7ce…     499 (ERC-6909)  ← Transfer 이벤트 없음
settle  라우터 → PM      2,241,466
take    PM → 수령자      31,316,167,330,635,321,344
```

훅이 가져간 499와 그 목적지는 익스플로러에 존재하지 않는 정보다.

## 3. 구현하면서 발견한 함정 3가지 (M1에 그대로 반영 필요)

기획서에 없던 내용이고, 몰랐으면 그림이 틀렸을 것들이다.

### 3.1 되돌려진 서브트리를 반드시 잘라내야 한다 — 가장 위험

callTracer는 **되돌려진(revert) 호출의 내부까지 전부 포함해서** 준다. 그리고 부모가 revert돼도
자식 프레임에는 `error` 필드가 안 붙는다. 부모만 붙는다.

라우터가 견적을 뽑으려고 `try { swap() } catch {}` 로 시뮬레이션한 뒤 되돌리는 패턴이 실제로 흔한데,
이걸 안 자르면 **일어나지도 않은 스왑을 그림에 그리게 된다.** 초기 구현에서 실제로 이것 때문에
4건이 틀렸고, 조상 중 하나라도 revert면 통째로 건너뛰도록 고쳐서 해결했다 (`walkEffective`).

M1에서 이 처리를 빠뜨리면 조용히 틀린 그림이 나온다. 에러가 안 나서 더 위험하다.

### 3.2 훅 권한 비트를 봐야 한다

훅이 델타를 리턴해도, 훅 주소 하위 14비트에 해당 `RETURNS_DELTA` 권한이 없으면
PoolManager가 그 값을 **무시한다.** 리턴값만 믿고 집계하면 틀린다.

권한은 주소 자체에 인코딩돼 있어서 RPC 호출 없이 읽을 수 있다 (`hookPermissions()`).
기획서 §11이 "훅 권한 비트 확인용"으로 v4 코어를 참고 목록에 넣은 건 정확한 판단이었다.

### 3.3 훅 델타는 `afterSwap`이 아니라 `swap` 프레임에서 정산해야 한다

`beforeSwap`만 가진 훅(`afterSwap` 권한 없음)이 실제로 존재한다. v4는 이 경우에도
`BeforeSwapDelta`를 적용하는데, `afterSwap` 호출은 트레이스에 안 나타난다.
`afterSwap` 프레임에서 훅 델타를 집계하면 이런 훅을 통째로 놓친다.

정산 지점은 상위 `swap` 프레임이고, 거기서 자식 콜백들을 모아 계산해야 맞다.
추가로 훅이 자기 자신을 호출해 스왑하는 경우 v4는 훅 회계를 건너뛴다 — 이것도 반영했다.

## 4. 열린 질문(§12)에 대한 답

**첫 지원 체인 → Base를 추천한다.**
훅이 붙은 풀을 거치는 트랜잭션 비율이 크게 다르다. Unichain 25.8%(89건 중 23건) vs
**Base 66.3%(98건 중 65건)**. 관측된 서로 다른 훅도 Unichain 12종 vs Base 24종.
"훅이 뭘 했는지 보여준다"가 제품의 핵심인데, Unichain은 방문자가 아무 해시나 넣으면
훅 없는 밋밋한 그림이 나올 확률이 훨씬 높다. 데모 임팩트는 Base가 낫다.
복원 로직은 체인 무관하게 동일하게 작동하므로(PoolManager 주소만 다름) 둘 다 지원해도 비용이 거의 없다.

**멀티홉 → 한 그림에 담을 수 있다.** 3개 훅이 얽힌 5-홉 트랜잭션(`0x74803911…`)도
노드 22개 / 엣지 47개로 복원됐다. 홉별 분리는 불필요하고, 레이아웃 문제로 다루면 된다.

**실패한 트랜잭션 → 지금 구조로는 안 된다.** 되돌려진 트랜잭션은 델타 제로 불변식이 성립하지 않아
검증 기준 (1)을 쓸 수 없고, §3.1의 서브트리 절단 로직과도 정면으로 충돌한다.
"어디서 멈췄는지"를 보여주는 건 가치 있지만 별도 모드로 설계해야 한다. v1 범위 밖으로 두는 걸 권한다.

**훅 매핑 유지보수(M4)** → 아직 답 없음. 다만 권한 비트는 주소에서 공짜로 읽히므로,
프로토콜명을 모르더라도 "이 훅은 스왑 전후에 개입하고 수수료를 가져갈 수 있음"까지는
매핑 테이블 없이 항상 표시할 수 있다. M4 전까지의 공백을 메우는 데 쓸 수 있다.

## 5. 리스크 표(§10) 업데이트

| 리스크 | M0 결과 |
|---|---|
| callTracer만으로 델타 복원 불가 | **해소.** 187/187 복원. 커스텀 트레이서 불필요 |
| `debug_traceTransaction` 비용/제한 | **실재 확인.** 아래 참조 |

무료 공개 RPC(dRPC)로 검증했고, 여기서 나온 제약이 있다:

- Unichain/Base 공식 퍼블릭 RPC와 publicnode는 `debug_traceTransaction`을 **막아놨다.**
  dRPC만 응답했다. 즉 아카이브 노드 접근은 선택이 아니라 필수다.
- Base 표본에서 **23건이 첫 시도에서 무료 플랜 타임아웃**이 났다. 재시도로 전부 성공했지만,
  큰 트랜잭션일수록 실패 확률이 높다. 기획서가 이미 적어둔 "결과 캐싱 / 예시 해시는 정적 JSON 고정"은
  선택 사항이 아니라 **필수**다. 스파이크에도 디스크 캐시를 넣었다.
- 유료 RPC 키 확보를 M2(첫 공개) 전제 조건으로 잡아야 한다.

## 6. M1이 물려받는 것

M0 코드는 버려도 된다고 했지만, 버릴 필요가 없는 부분이 나왔다.

- `reconstruct.mjs` — 델타 복원 엔진. v4 회계 규칙이 전부 들어있고 187건으로 검증됐다.
  M1에서 다시 쓰는 걸 권한다. 여기를 다시 짜면 위 함정 3개를 다시 밟는다.
- `graph.mjs` — 복원 결과를 **기획서 §7 데이터 모델 그대로** 뽑는다.
  `engineer` 필드까지 채워져 있어서 M3 모드 토글의 근거가 이미 준비돼 있다.
  훅이 호출한 외부 컨트랙트도 `type: "external"` 노드로 나온다 (§7 "열린 집합" 요구사항 충족).
- `fixtures/` — 검증된 그래프 JSON 5건. 해시 하드코딩 대신 이걸 쓰면
  M1을 RPC 없이 순수 렌더링 작업으로 진행할 수 있다.

M1의 남은 일은 사실상 **SVG 렌더링뿐**이다. 데이터 문제는 여기서 끝났다.

### 실행 방법

```bash
node collect-pools.mjs unichain 8 450 swap   # 풀별 표본 수집
node verify.mjs --file pools-unichain.txt    # 복원 + 이중 검증
node verify.mjs -v <txHash>                  # 단건 상세
node stats.mjs pools-unichain.txt            # 코퍼스 통계
node graph.mjs <txHash>                      # §7 JSON 출력

CHAIN=base RPC_URL=https://base.drpc.org node verify.mjs --file base-sample.txt
```
